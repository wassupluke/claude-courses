The Token Economy

Every interaction with Claude — whether in the API, Claude.ai, Claude Code, or Cowork — is billed in tokens. One token is roughly 4 characters or 0.75 English words. You pay for tokens going in (input) and tokens coming out (output). Output tokens cost more than input tokens on every model.

This sounds simple, but the surface area of what counts as a token is vast: your messages, Claude's replies, system prompts, tool definitions, document contents, images, and even conversation history all contribute. The good news is that the optimization levers are equally numerous — and they stack.

💡
The core insight

Efficiency isn't about being stingy — it's about maximizing signal density. Every token you send should earn its place. Every token Claude generates should be purposeful. The techniques in this course aren't tricks; they're a systematic approach to that principle.

The optimization stack

The techniques in this course stack multiplicatively. Here are the five highest-ROI levers, in rough order of impact:

Before you can optimize, you need to know exactly where tokens are going. Every API request sends more than you might expect, and in agentic workflows the real costs are often hidden inside tool definitions and conversation history that grows with every turn.

⚠️
The stateless API is your biggest hidden cost driver

The Messages API has no server-side memory. Every single turn in a multi-turn conversation re-sends all previous messages as input tokens. A 20-turn conversation where each turn averages 500 tokens means Turn 20 sends 10,000 tokens of history alone — before you've typed a word of your actual question.

Extended thinking tokens

Extended thinking is billed as output tokens at standard rates. The thinking content itself is visible to you but it's automatically stripped from subsequent turns — meaning thinking does not accumulate in your conversation history. However, you're still paying for the full thinking process, not just the summarized response.

The minimum thinking budget is 1,024 tokens. For newer models (Opus 4.6, Sonnet 4.6), the effort parameter replaces manual budget tuning. Setting effort: "low" may skip thinking entirely for simple queries, which is often the right call.

Using the Token Counting API

Before sending a large or expensive request, use the free /v1/messages/count_tokens endpoint to measure it first. It accepts the exact same payload format as /v1/messages — just point it at the counting endpoint instead.

POST /v1/messages/count_tokens
{
  "model": "claude-sonnet-4-6",
  "system": "Your system prompt here...",
  "tools": [ /* your tool definitions */ ],
  "messages": [
    {"role": "user", "content": "What is the weather like?"}
  ]
}
// Returns: {"input_tokens": 843}

Prompt Caching: The Biggest Lever

Prompt caching is the highest-impact optimization available to API users. When Claude processes the same content repeatedly — your system prompt, tool definitions, a large reference document — it can store a representation of that content and reuse it. Cache reads cost 10% of the normal input token price. That's a 90% discount.

How caching works

You mark content for caching with "cache_control": {"type": "ephemeral"} on specific content blocks. Claude checks whether it has already processed that content in a recent request. If yes — a cache hit — you pay 10% of the normal rate. If no — a cache miss — you pay a cache write premium (1.25× or 2.0× depending on TTL), but subsequent requests that hit will be cheap.

OperationCost vs. normal inputWhen it applies
Cache write (5 min TTL)1.25× (25% premium)First request; cache miss
Cache write (1 hr TTL, beta)2.0× (100% premium)Optional extended TTL
Cache read (hit)0.1× (90% savings)Subsequent requests within TTL

The TTL refreshes on every cache hit at no additional cost. A 5-minute cache that gets hit every 3 minutes effectively stays alive indefinitely. Break-even occurs at approximately 2 cache hits for the 5-minute TTL.

What can be cached

The cache applies in a strict top-down order: tools → system → messages. You can place up to 4 cache breakpoints per request. Content that can be cached includes tool definitions, system messages, text messages (both user and assistant turns), images, documents, and tool results.

💡
Always cache your system prompt and tool definitions first

These are the most stable content across requests and the easiest win. If your system prompt is 2,000 tokens and you make 100 API calls per day, caching it saves roughly 180,000 tokens per day at Sonnet pricing — about $0.54/day saved for essentially zero implementation effort.

Minimum token thresholds

Content must meet a minimum token count before it qualifies for caching. Short content cannot be cached.

Model familyMinimum cacheable tokens
Claude Opus 4, Opus 4.1, Sonnet 4, 4.5, 3.7, Haiku 3.51,024 tokens
Claude Haiku 32,048 tokens
Claude Opus 4.5, Haiku 4.54,096 tokens

Caching a system prompt — example

{
  "model": "claude-sonnet-4-6",
  "system": [
    {
      "type": "text",
      "text": "You are an expert clinical research assistant...\n[2,000+ tokens of detailed instructions]",
      "cache_control": {"type": "ephemeral"}
    }
  ],
  "messages": [{"role": "user", "content": "Summarize this adverse event report..."}]
}

Cache invalidation rules

The cache is position-sensitive. Modifying content at any level invalidates that level and everything below it. Toggling web search or citations invalidates the system + messages cache. Changing tool definitions invalidates the entire chain. This is why you should keep your most volatile content at the bottom of the prompt — put stable content (tool defs, system prompt) at the top where it won't be invalidated by message-level changes.

The tiered architecture pattern

Production teams with high-volume workflows often run a three-tier system rather than using one model for everything. This is the most impactful model selection strategy for applications:

1

Haiku — routing, classification, sub-agents

Handle intent detection, content classification, ticket triage, and simple extraction. Haiku 3 delivers ~90% of Sonnet's accuracy on these tasks at 12× lower input cost.

2

Sonnet — standard generation and analysis

Your default for drafting, summarization, code generation, question answering, and most user-facing interactions. The best intelligence-per-dollar across the Claude lineup.

3

Opus — complex multi-step reasoning and highest stakes

Reserve for tasks where model errors are costly: large-scale code refactoring, complex multi-document synthesis, agentic workflows requiring deep reasoning, and cases where Sonnet's output quality isn't sufficient.

Thinking: effort vs. budget

For Opus 4.6 and Sonnet 4.6, the effort parameter replaces manual budget tuning. Sonnet 4.6 defaults to high effort — set it explicitly if you want a different level to avoid unexpected latency and costs:

  • effort: "low" — May skip thinking entirely. Best for simple queries, formatting, lookup tasks. Big cost saver.
  • effort: "medium" — Balanced reasoning. Good default for mixed workloads where you want thinking without high cost.
  • effort: "high" — Deep reasoning. Sonnet 4.6's actual default if not set explicitly.
  • effort: "max" — Maximum thinking. Reserve for hardest, longest-horizon problems.

For older models, if you're using a manual budget, the minimum is 1,024 tokens and the practical sweet spot for complex tasks starts at 16K. Above 32K, you risk system timeouts — use the Batch API for those cases.

Context Window Management

All current Claude models share a 200,000-token context window. A 1M-token extended context is available in beta for Sonnet 4, 4.5, 4.6 and Opus 4.5, 4.6. But bigger isn't always better — understanding how context degrades performance is as important as knowing how large it is.

Context window ≠ effective working memory

Transformers compute pairwise attention between every token and every other token. As context grows, each additional token dilutes the attention budget for existing tokens. Anthropic's own research shows a U-shaped performance curve: information at the beginning and end of the context is recalled most accurately, while content in the middle suffers most. In studies on earlier models, mid-context accuracy dropped to roughly 27%.

🚨
Context rot is real

More tokens in context doesn't mean Claude pays more attention to all of them. Anthropic engineering calls this "context rot" — the model has a finite attention budget, and stuffing the context window degrades precision on everything. The optimal strategy is the smallest possible set of high-signal tokens, not the largest.

What fills context fastest in agentic sessions

In long agentic sessions (Claude Code, Cowork, API tool-use), context fills much faster than in simple chat. The culprits in order of severity:

🔧

Tool results

Every file read, search result, and command output stays in history. A single web fetch: 2,500–125,000 tokens. They accumulate on every turn.

📜

Conversation history

Re-sent in full on every API call. A 20-turn conversation sends all 20 turns as input on Turn 21.

🖼️

Images

~1,600 tokens each. Multiple images compound quickly. Only send images when visual analysis is actually needed.

📄

PDFs

1,500–3,000 tokens per page (text + image rendering). A 20-page document is 30,000–60,000 tokens before you've asked a question.

Placement matters: put queries last

For long-context requests with multiple documents, place the query at the very end of the prompt. This positioning improvement alone can boost response quality by up to 30% on complex multi-document inputs. Structure documents with XML tags and metadata:

<documents>
  <document index="1">
    <source>protocol-v3.pdf</source>
    <document_content>...</document_content>
  </document>
  <document index="2">
    ...
  </document>
</documents>

Ask Claude to quote before answering

On long-context tasks, instruct Claude to locate and quote the relevant passage before answering. This acts as a forced attention mechanism — the quoting step "cuts through the noise" of a large context and anchors the response to the actually-relevant content rather than relying on imprecise mid-context recall.

✅ Effective long-context instruction
Before answering, quote the specific section from the documents that is most relevant to the question. Then answer based on that quoted section.

Optimal Session Setup

How you set up a session before the first message determines a large part of its efficiency. Good architecture eliminates the per-session overhead of re-explaining context, re-establishing conventions, and recovering from misaligned assumptions.

Claude Projects: persistent context done right

Projects provide a persistent knowledge base that Claude references across all chats in the project. The critical design question is knowing what goes where:

LocationWhat belongs hereLoaded how
Project instructionsRole, tone, standing rules, persistent behavioral contextEvery conversation, in full
Knowledge base filesReference docs, specs, codebases, data filesOn-demand via RAG when approaching context limits
Per-message contextTask-specific data, current documents, one-off queriesOnly in that message
💡
RAG activates automatically in Projects

When your project knowledge base approaches the context window limit, Claude automatically switches to RAG (retrieval-augmented generation) — fetching only the relevant portions of knowledge files rather than loading everything. This effectively multiplies your usable knowledge base by up to 10×. Use descriptive filenames; they directly improve retrieval accuracy.

Claude Code: CLAUDE.md and the memory system

Claude Code loads context from a hierarchy of CLAUDE.md files at session start. This means you can encode project conventions, coding standards, and architectural decisions once — and they're available in every session without any conversation overhead.

1

~/.claude/CLAUDE.md — Global user preferences

Your personal coding style, preferred tools, global conventions. Loaded into every Claude Code session regardless of project.

2

CLAUDE.md in project root — Project rules

Architecture decisions, dependency choices, test conventions, naming patterns. Loaded automatically on every session in this repo.

3

Child directory CLAUDE.md files — Module-specific context

Documentation for specific subsystems. Loaded on demand when Claude navigates into that directory.

4

CLAUDE.local.md — Private per-project preferences

Personal overrides not for the team (auto-gitignored). Your preferred debug flags, local paths, etc.

CLAUDE.md supports an @path/to/file import syntax for pulling in external documentation. Keep CLAUDE.md files specific and brief — "Use 2-space indentation" beats "Format code properly."

API system prompts: structure for cacheability

Organize your system prompt so stable content is at the top and volatile content is at the bottom. Cache breakpoints partition the content — any change invalidates the breakpoint it touches and everything below it. The hierarchy: tool definitions → static system context → dynamic user-specific data → per-request instructions.

system: [
  // Block 1: Tool definitions (most stable — cache this)
  {"type": "tool_definitions", "cache_control": {"type": "ephemeral"}},

  // Block 2: Static system context (stable — cache this)
  {"type": "text", "text": "You are a...[long stable instructions]",
   "cache_control": {"type": "ephemeral"}},

  // Block 3: Dynamic user context (changes per user — don't cache)
  {"type": "text", "text": "Current user: " + user.name + "..."}
]

Cowork: global and folder instructions

Cowork's two-level instruction system mirrors the Projects + per-message structure. Global instructions (Settings → Cowork → Edit) apply to every session. Folder instructions activate when Claude is working in a specific directory and encode project-specific context, naming conventions, and compliance rules. Think of it as: global = who you are, folder = what this project is.

Waste Patterns to Eliminate

Most token waste falls into a handful of repeatable anti-patterns. Identifying them in your own workflow is the fastest path to efficiency gains that don't require any API changes.

Anti-pattern 1: Explaining things Claude already knows

Claude has deep knowledge of XML, JSON, Markdown, common programming languages, standard frameworks, and widespread conventions — baked into its training. You don't need to explain these formats; you just use them. What you do need to provide is your specific context: your norms, your codebase's conventions, your task-specific requirements.

❌ Wasteful — explaining the obvious
JSON is a data format that uses key-value pairs. Keys must be strings. Values can be strings, numbers, booleans, arrays, or objects. Please return your response as a JSON object with the following keys: "name" (string), "age" (number), "active" (boolean).
✅ Efficient — just use the format
Return JSON with keys: "name" (string), "age" (number), "active" (boolean).

Anti-pattern 2: Anti-laziness prompts on Claude 4.x

On Claude 3.x, prompts like "be thorough," "think carefully," and "don't be lazy" were useful workarounds for a less proactive model. On Claude 4.x models, Anthropic explicitly warns that these phrases "amplify already-proactive behavior and can cause runaway thinking or write-then-rewrite loops." They don't add quality — they add tokens.

🚨
Remove these from Claude 4.x prompts

"Be thorough" · "Think carefully" · "Do not be lazy" · "You MUST use this tool" · "CRITICAL: Always..." · Aggressive all-caps instructions. These were Claude 3.x workarounds. They cause over-generation and excessive tool calling on Claude 4.x.

Anti-pattern 3: Monolithic prompts

A single 5,000-token prompt for a complex multi-step task is often worse than three focused 500-token prompts chained together. Each subtask gets Claude's full attention. Errors are isolated and easier to trace. Independent subtasks can be parallelized. The "chain of prompts" pattern scales far better than the "one mega-prompt" approach.

Anti-pattern 4: Images when text suffices

Image processing costs ~1,600 tokens per image at typical resolutions. Don't send images when a text description of the relevant content would work equally well. And never send oversized images — anything over 1,568 pixels on the long edge or ~1.15 megapixels gets resized automatically, but the preprocessing still adds latency. Very small images (under 200px on any edge) actually degrade quality.

Anti-pattern 5: Loading all tool definitions upfront

Every tool definition you load adds fixed overhead to every request, whether or not that tool is used. Anthropic's internal "Tool Search" feature reduces average token usage by 37% on complex tasks by discovering tools on-demand rather than loading all definitions upfront. Apply the same principle to your own systems: load tool definitions lazily when the task calls for them rather than in every system prompt.

Anti-pattern 6: Verbosity in prompts and outputs

Ask for paragraph or sentence count limits rather than word counts — LLMs count tokens, not words, making word-count instructions unreliable. Set max_tokens as a hard ceiling. Ask for what you want in terms of format: "Write in flowing prose" rather than "Don't use bullet points." Claude 4.5+ models are naturally more concise and will skip detailed summaries for efficiency unless you ask for them.

Anti-pattern 7: Stale context in agentic sessions

In Claude Code, an open session accumulates context from every file read, command output, and tool call. When you switch to a completely different task within the same session, that accumulated context is irrelevant noise that still consumes tokens on every subsequent turn. Use /clear when switching to unrelated work. Use /compact to summarize context when it's getting large but you need to preserve thread.

Advanced Stacking: Combining Optimizations

Individual optimizations are useful. Combined, they're transformative. The techniques in this module are how production teams achieve 55–95% cost reductions while maintaining or improving output quality.

The Batch API: 50% off non-urgent work

The Message Batches API processes up to 10,000 requests per batch within 24 hours (typically under 1 hour) at a flat 50% discount on both input and output tokens. This discount stacks with prompt caching — a cached read on a batched request costs 0.1× of the already-halved batch price.

OptimizationCombined effect
Prompt caching only90% off cached input tokens
Batch API only50% off all tokens
Caching + Batching (cache hit)95% off cached input tokens
Haiku instead of Sonnet + Caching + Batching~98% vs. Sonnet without optimizations

Ideal batch use cases: content generation pipelines, data extraction from document corpora, evaluation suites and evals, synthetic training data generation, overnight report generation. Not suitable for: real-time user-facing interactions, tasks requiring immediate results.

Token-efficient tool use

Token-efficient tool use is built into all Claude 4 models and reduces output token consumption for tool calls by up to 70%, with average real-world reductions of around 14%. Early adopters report significant cost savings on agentic workflows where tool calling is frequent. For Claude 3.7 Sonnet, enable it with the beta header token-efficient-tool-use-2025-02-19.

Structured outputs: eliminate retry waste

Native structured outputs (generally available on Claude 4.x models) guarantee valid JSON conforming to your schema, eliminating the most common cause of agentic workflow failures: parsing errors that require costly retry loops. Two mechanisms:

  • JSON output format — Set output_config: {"format": "json"} to guarantee valid JSON in the response.
  • Strict tool use — Set "strict": true on a tool definition for guaranteed type-safe parameters matching your schema.

Note: prefilling (injecting content into the last assistant turn) is deprecated on Claude 4.6 models (Opus 4.6, and future 4.6+ releases). Use structured outputs or system prompt instructions instead.

Subagents: context isolation at scale

Subagents are the key to long-horizon tasks that would otherwise exhaust the context window. Each subagent gets its own fresh context window, explores as extensively as needed, and returns only a condensed 1,000–2,000 token summary to the parent agent. This prevents context bloat in the main conversation.

ℹ️
Subagent token economics

Agent teams using subagents in plan mode consume approximately 7× more tokens than standard sessions because each teammate maintains its own context window. This sounds expensive — but the alternative for truly complex tasks is a single overfull context window where quality degrades. For the right tasks, 7× the tokens delivers 10× the quality.

In Claude Code, subagents are defined as Markdown files in .claude/agents/ with YAML frontmatter specifying name, tools, and system prompt. The built-in Task tool provides a general-purpose subagent without any configuration. Use subagents when tasks can run in parallel, require isolated context, or involve independent workstreams. Work directly when tasks are simple, sequential, or require shared context between steps.

Few-shot prompting: quality per token

The optimal number of examples in a few-shot prompt is 3–5 for most tasks. More examples improve performance on complex tasks, but Anthropic warns against "stuffing a laundry list of edge cases." Instead, curate diverse, canonical examples that cover the behavioral space you care about. Wrap examples in <example> tags. Quality and diversity matter more than quantity.

Platform Playbooks

The principles are consistent across Claude surfaces, but the implementation looks different depending on where you're working. These playbooks distill the course into concrete actions for each platform.

🔌 API Playbook

1

Cache system prompts and tool definitions immediately

Mark them with cache_control: ephemeral. This is the highest-ROI single change you can make to an existing API integration.

2

Start with Sonnet; downgrade to Haiku for proven-simple tasks

Run A/B evals. For classification, routing, and extraction, Haiku often matches Sonnet quality at a fraction of the cost.

3

Move async workloads to the Batch API

Any pipeline that doesn't require real-time results should be batched. 50% off, zero quality impact.

4

Use structured outputs to eliminate retries

Every parse failure is wasted tokens and latency. Structured outputs pay for themselves in reliability.

5

Set max_tokens and use the Token Counting API

Hard ceilings prevent runaway output costs. Count before you send on expensive requests to catch bloat before it's billed.

💻 Claude Code Playbook

1

Write a CLAUDE.md in every project root

Architecture, conventions, preferred patterns. Encode once, available every session. No per-session overhead.

2

Use /clear between unrelated tasks

Stale context is expensive and degrades quality. Start fresh when the topic changes.

3

Use /compact with a focus parameter before context fills

/compact focus on the authentication changes keeps the relevant thread without the accumulated noise.

4

Be specific in requests

"Add input validation to the login function in auth.ts" beats "improve this codebase" — specificity prevents broad file scanning and scattered tool calls.

5

Reduce thinking budget for routine tasks

The default Claude Code thinking budget is 31,999 tokens. For simple tasks, set MAX_THINKING_TOKENS=8000 or less. Use /config to adjust per session.

📁 Claude Projects Playbook

1

Write tight project instructions

Role, tone, standing rules. These load every conversation. Keep them focused — not a novel.

2

Name knowledge files descriptively

Filenames directly improve RAG retrieval. "2024-Q3-safety-monitoring-report.pdf" beats "report.pdf".

3

Reference specific files in queries

"Based on the protocol document, what are the inclusion criteria?" helps Claude retrieve the right file rather than guessing.

🤖 Cowork Playbook

1

Use global instructions for persistent identity

Your role, preferred formats, safety rules. Set once, active every session.

2

Use folder instructions for project context

Protocol names, naming conventions, compliance rules. Scope them to the specific project folder.

3

Write GOAL-framework prompts

Goal, Output format, Approach constraints, Location. Specificity eliminates mid-task check-ins and re-runs.

4

Queue tasks and step away

Cowork is designed for async execution. Queue multiple tasks upfront rather than babysitting each one interactively.

💬 Claude.ai Chat Playbook

1

Use Projects for repeated context

If you find yourself re-explaining your role, project, or conventions at the start of every chat — those belong in a Project's instructions.

2

Start new chats for genuinely new topics

Long conversation history in an existing chat adds input token overhead for every new message. A fresh chat for a fresh topic is often the efficient choice.

3

Put your actual question at the end

Especially for long-context requests: context first, question last. Up to 30% quality improvement on complex multi-document prompts.
