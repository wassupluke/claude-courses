The Context Economy

Claude Code is an agent that lives in your terminal, reads your files, runs commands, and edits code on your behalf. Everything it does flows through one finite resource: the context window — the working memory that holds your instructions, the conversation, every file it has read, and every command output it has seen.

Most current Claude models give Claude Code a 200,000-token context window (Sonnet offers a 1M-token beta). That sounds enormous — until you realize a single agentic session can read dozens of files, run test suites, and grep through a codebase, each result staying in context and re-sent on every turn. Efficiency in Claude Code isn't about spending less money; it's about keeping that window full of signal and empty of noise.

💡
The core insight

A Claude Code session is only as good as its context. Every token in the window either helps Claude solve your task or distracts from it. The techniques in this course are one idea applied eight ways: keep the working set small, relevant, and purposeful — and let Claude do more before the window fills.

The efficiency stack

These levers compound. A well-set-up session with the right model, disciplined context hygiene, and delegation to subagents does far more useful work than a single sprawling conversation. Here are the five highest-ROI levers, in rough order of impact:

🧹

Context Hygiene

/clear between tasks and /compact before the window fills. The single biggest lever for quality and speed. Module 4.

📋

Encode conventions once; load them free every session. No re-explaining, no drift. Module 5.

🧩

Subagents

Isolate exploration in a fresh context; only a summary returns to the main thread. Module 7.

What Actually Fills Your Context

Before you can manage context, you need to know where it goes. In an agentic session the biggest consumers are rarely your messages — they're the tool results and accumulated history that grow with every turn.

The anatomy of a Claude Code session

What's in context Typical weight Notes
System prompt & tool definitions Fixed overhead Built in; loaded once, cached across the session
CLAUDE.md files Loaded at session start Every relevant CLAUDE.md in the hierarchy, in full
File reads Grows fast Every file Claude reads stays in history
Command & tool output Grows fast Test runs, greps, builds, logs — all retained
Conversation history Grows linearly All prior turns are part of every new request
MCP server tool definitions Fixed per server Added to every request whether used or not
Extended thinking Per-turn, not accumulated Billed as output; stripped from later turns
⚠️
Tool output is the silent context killer

A single cat of a large file, a verbose test run, or a broad grep can drop tens of thousands of tokens into the window in one turn — and it stays there for the rest of the session. The most common cause of a session going sideways isn't a bad model; it's a window stuffed with output Claude no longer needs.

See it for yourself: /context

Claude Code ships with a /context command that visualizes exactly how your window is currently allocated — system prompt, tools, MCP servers, memory files, and conversation. Run it when a session feels sluggish or confused; you'll almost always find a bloated category you can trim.

✅ Habit worth building
Run /context before starting a big task and again when responses start to feel unfocused. If MCP tools or old file reads dominate the window, that's your signal to clear, compact, or disconnect a server.

Extended thinking doesn't accumulate

When Claude Code "thinks" (triggered by phrases like think, think hard, or ultrathink, or configured via MAX_THINKING_TOKENS), that reasoning is visible to you but automatically stripped from subsequent turns. Thinking is a per-turn cost, not a permanent context tax — so use it freely on hard problems, and dial it down for routine edits where deep reasoning just adds latency.

Prompt Caching: Working For You Already

Prompt caching lets Claude reuse a stored representation of content it has already processed — your system prompt, tool definitions, CLAUDE.md, and the growing conversation prefix. A cache read costs a small fraction of processing that content fresh. The good news for Claude Code users: this is handled automatically. You don't set cache breakpoints or write any config.

Why it matters to you anyway

Caching is a prefix match: Claude caches content from the beginning of the request up to a breakpoint, and any change in that prefix invalidates everything after it. Understanding this explains a lot of Claude Code behavior — and points at habits that keep the cache warm.

Action Effect on the cache
Continuing the same conversation Reuses the whole prior prefix — cheap and fast
Editing CLAUDE.md mid-session Changes an early part of the prefix — invalidates below it
Adding or removing an MCP server Changes tool definitions at the top — full re-process
Switching models mid-task Caches are per-model — the new model starts cold
💡
Keep the front of the window stable

The practical takeaway: don't churn your CLAUDE.md, tool set, or model in the middle of a task. Set them up front and let the cache do its job. Each of those changes forces Claude to re-read the whole prefix — slower turns for no benefit. Save the CLAUDE.md edits and MCP tweaks for between tasks, right after a /clear.

What this means in practice

You mostly get caching for free — but you can help it along. Long-lived sessions on a stable configuration are the cheapest and fastest, because the shared prefix keeps getting reused. Sessions where you constantly reconfigure tools or rewrite memory files pay the cold-cache penalty over and over. Efficiency here is a byproduct of the discipline you're learning everywhere else in this course.

Model Selection: Matching Power to Task

Claude Code lets you choose which model drives your session with the /model command, and you can pick a different model for subagents. The right model isn't always the most capable one — it's the one that reliably does the job at the speed and cost you want. Reaching for the top-tier model on a trivial rename is like hiring a neurosurgeon to take your blood pressure.

The Claude Code lineup

Model Best for in Claude Code
Opus Complex multi-file refactors, deep debugging, long-horizon autonomous work, architecture decisions
Sonnet The default workhorse — best intelligence-per-dollar for most day-to-day coding and agentic tasks
Haiku Fast, cheap, latency-sensitive work — simple edits, quick lookups, and subagents doing bounded tasks
ℹ️
Start with the default, adjust deliberately

For most work, the default model gives the best balance of capability and speed. Reach for Opus when you've confirmed the task genuinely needs deeper reasoning — a gnarly bug, a large-scale refactor, a design you can't fully specify. Drop to Haiku for high-volume, well-scoped operations where a bigger model is over-qualified.

The tiered pattern in one session

You don't have to run the whole session on one model. A powerful pattern: drive the main thread with a capable model for planning and coordination, and delegate bounded, parallel work to subagents running a cheaper, faster model. The main agent stays sharp; the grunt work runs cheap.

1

Haiku — scoped, high-volume subtasks

Searching for usages, summarizing a directory, running and reporting a bounded check. Fast turnaround where deep reasoning isn't required.

2

Sonnet — standard implementation

Writing and editing code, following conventions, most interactive coding. The default for a reason.

3

Opus — the hard 10%

Reserve for tasks where errors are expensive: sprawling refactors, subtle concurrency bugs, decisions that shape the codebase for months.

💡
Don't switch models mid-task

Because caches are per-model, flipping models in the middle of a task discards the cached prefix and starts cold. Choose your model at the start of a task (or per subagent), then leave it. If you need a different tier, that's usually a signal to /clear and start a fresh, well-scoped session.

Context Window Management

This is the module that changes how you use Claude Code. Managing the window actively — clearing it, compacting it, and steering what goes into it — is the highest-leverage skill you can build.

Bigger context ≠ better performance

A large context window is capacity, not attention. As context grows, the model has more tokens competing for a finite attention budget, and precision on any single detail can degrade. Anthropic engineering describes this as "context rot": a window stuffed with stale file reads and old command output makes Claude worse at the task in front of it, not better. The goal is the smallest set of high-signal tokens that gets the job done.

🚨
A confused session usually has a bloated window

When Claude Code starts making odd choices, repeating itself, or losing the thread, the reflex shouldn't be to explain harder — it should be to check the window. Nine times out of ten the fix is /clear or /compact, not a longer prompt.

The two commands that matter most

1

/clear — wipe context between tasks

Resets the conversation to a clean slate while keeping your CLAUDE.md and configuration. Use it every time you switch to unrelated work. The context from fixing the login bug is pure noise when you move on to the billing report.

2

/compact — summarize when you need continuity

Condenses the conversation into a summary that preserves the thread while shedding the accumulated bulk. Use it mid-task when the window is filling but you still need what came before. Add focus to keep what matters: /compact focus on the auth refactor.

ℹ️
Auto-compact is a safety net, not a strategy

Claude Code will automatically compact as the window approaches its limit, but auto-compaction is a last resort — it summarizes on the model's terms, not yours, and can lose detail you cared about. Compacting deliberately, with a focus instruction, keeps the thread you actually need. Better still: /clear often enough that you rarely hit the limit.

/rewind — undo a wrong turn

When Claude heads down the wrong path, you don't have to unwind it conversationally (which just adds more tokens). /rewind lets you roll the conversation — and optionally the code changes — back to an earlier checkpoint, so you can retry from a clean state instead of arguing your way out of a mess.

Steer what enters the window

The cheapest context to manage is the context you never let in. Be specific about scope so Claude reads the two files it needs instead of scanning twenty. Ask for targeted searches over broad ones. When a command produces mountains of output, ask Claude to pipe it through a filter rather than reading the whole thing.

✅ Scope-aware request
Add input validation to the login() function in src/auth/session.ts. Don't touch other files.

Optimal Session Setup

How you set up a project before the first prompt determines how much per-session overhead you pay forever after. Good setup eliminates the endless re-explaining of conventions, tools, and architecture that otherwise eats the start of every conversation.

CLAUDE.md: the memory hierarchy

Claude Code loads context from a hierarchy of CLAUDE.md files at session start. Encode your conventions, standards, and architectural decisions once, and they're available in every session with zero conversation overhead. Knowing what goes where is the whole game:

1

~/.claude/CLAUDE.md — global user preferences

Your personal style, preferred tools, and standing rules. Loaded into every Claude Code session on your machine, regardless of project.

2

CLAUDE.md in the project root — team rules

Architecture, dependency choices, test conventions, naming patterns. Checked into the repo so the whole team (and their Claude sessions) share the same context.

3

Subdirectory CLAUDE.md — module-specific context

Documentation for a specific subsystem, pulled in on demand when Claude works in that directory. Keeps niche detail out of the root file.

4

CLAUDE.local.md — private overrides

Personal, gitignored notes that aren't for the team — local paths, debug flags, scratch reminders. (The @path import syntax is the modern way to pull in external files; see below.)

💡
Keep CLAUDE.md tight — it's loaded every session

CLAUDE.md is not a wiki. Every token in it is loaded into every session's context, so bloat here is a permanent tax. "Use 2-space indentation" beats a paragraph on formatting philosophy. Prefer specific, high-signal rules over prose, and use the @path/to/file import syntax to pull in longer reference docs only when they're relevant.

The /init shortcut

Not sure what to put in a project's CLAUDE.md? Run /init in a repo and Claude Code will explore the codebase and draft one for you — build commands, structure, conventions. Treat the output as a starting point to trim and sharpen, not a finished artifact.

Custom slash commands and tools

Repeated multi-step prompts belong in reusable slash commands (Markdown files in .claude/commands/). Instead of re-typing "run the tests, then fix any failures, then update the changelog" every time, you save it once and invoke /fix-and-log. Less typing, consistent behavior, and a shared prefix that caches well.

Waste Patterns to Eliminate

Most wasted context in Claude Code follows a handful of repeatable anti-patterns. Spotting them in your own workflow is the fastest way to sessions that stay sharp and finish more work.

Anti-pattern 1: The never-ending session

Running task after unrelated task in one long conversation is the most common mistake. Each task leaves its file reads and command output behind, and by task four Claude is wading through the wreckage of tasks one through three. /clear between unrelated tasks isn't housekeeping — it's how you keep quality high.

Anti-pattern 2: Vague, sprawling prompts

"Improve this codebase" invites Claude to read everything and touch anything, flooding the window and producing scattered changes. Specificity is efficiency.

❌ Vague — triggers broad scanning
Look through the project and improve the error handling everywhere it needs it.
✅ Scoped — one file, one goal
Wrap the network calls in api/client.ts with retry and a typed error result. Leave the rest of the file alone.

Anti-pattern 3: Anti-laziness prompting

Aggressive instructions like "be thorough," "think carefully about everything," or "you MUST check every file" were once workarounds for less proactive models. On current Claude models they amplify already-proactive behavior, causing runaway exploration and over-editing. State the goal and the scope; let the model do the rest.

🚨
Retire these from your prompts

"Be thorough" · "Check everything" · "Do not be lazy" · "CRITICAL: you MUST..." · aggressive all-caps demands. They push current models toward over-exploration and over-editing — exactly the behavior that fills your context and produces sprawling diffs.

Anti-pattern 4: Loading MCP servers you don't need

Every connected MCP server injects its tool definitions into every request, whether or not you use them — fixed overhead that also sits at the front of the cache prefix. Connect the servers a task actually needs, and disconnect ones you're not using. A pile of idle MCP tools is pure context tax.

Anti-pattern 5: Reading whole files when you need a slice

Asking Claude to read an entire 2,000-line file to change one function drops the whole thing into context. Point it at the relevant section, or let it search for the symbol first. The targeted read leaves room for the actual work.

Anti-pattern 6: Explaining what the model already knows

Claude knows your languages, frameworks, and standard tools. You don't need to explain what a Git rebase is or how JSON works — you need to provide your context: your conventions, your architecture, your constraints. Spend your tokens on what's specific to you.

Subagents, Skills & Plan Mode

The techniques so far keep a single session lean. These take it further — letting Claude Code do more work before the window fills, and structuring hard tasks so they stay on track.

Subagents: context isolation at scale

Subagents are the key to long-horizon work that would otherwise exhaust the window. Each subagent gets its own fresh context window, explores as much as it needs — reading files, running searches, digging through output — and returns only a condensed summary to the main thread. All that exploration never touches your main conversation.

ℹ️
The economics of delegation

A subagent that reads thirty files to answer one question would have dumped all thirty into your main window. Instead, it burns its own context and hands back a paragraph. You trade some extra total work for a main thread that stays clean and focused — a great deal on genuinely complex tasks, and often the only way to finish them at all.

The built-in Task tool gives you a general-purpose subagent with no configuration. For repeatable roles, define custom subagents as Markdown files in .claude/agents/ with YAML frontmatter specifying the name, allowed tools, and even a different model. Use subagents when work can run in parallel, requires isolated exploration, or is an independent workstream. Work directly when tasks are simple, sequential, or need shared context.

Skills: expertise loaded on demand

Skills package task-specific instructions and helper files that Claude loads only when relevant. A short description sits in context by default; the full skill loads when the task calls for it — so you get deep, specialized guidance without paying for it on every unrelated turn. It's progressive disclosure applied to your own know-how.

Plan mode: think before you touch

Plan mode lets Claude research and propose an approach without making any edits until you approve. For a multi-step change, this is efficiency in two ways: you catch a wrong approach before it produces a sprawling diff you have to unwind, and the plan itself becomes a compact, high-signal anchor for the execution phase. Cheap planning up front beats expensive rework later.

✅ Plan-first for complex changes
For a large refactor, enter plan mode, review the proposed steps, and only then let Claude execute. A five-minute plan review saves a fifty-file cleanup.

Hooks: automate the routine

Hooks let you run deterministic shell commands at defined points — for example, auto-formatting after every edit, or running a linter before a change is accepted. Moving routine checks into hooks means Claude doesn't have to spend a conversational turn (and the context) deciding to run them. The work still happens; it just stops costing window.

The Claude Code Playbook

The principles are consistent; this playbook distills the course into concrete habits you can adopt today. Work through them in order — each builds on the last.

💻 Everyday session hygiene

1

/clear between unrelated tasks

The single highest-ROI habit. Stale context degrades quality and slows every turn. Start fresh when the topic changes.

2

/compact with a focus before the window fills

When you need continuity but context is growing, /compact focus on X keeps the thread and sheds the noise. Don't wait for auto-compaction to decide for you.

3

Watch the window with /context

Check allocation when a session feels off. A bloated category is your cue to clear, compact, or disconnect a server.

4

/rewind instead of arguing

When Claude takes a wrong turn, roll back to a checkpoint and retry — cheaper and cleaner than talking your way out of it.

📋 Project setup

1

Write a tight CLAUDE.md in every project root

Architecture, conventions, build and test commands. Run /init to draft it, then trim to high-signal rules. Keep it small — it loads every session.

2

Encode repeated workflows as slash commands

Multi-step prompts you type often belong in .claude/commands/. Consistent behavior, less typing, better caching.

3

Connect only the MCP servers a task needs

Idle servers are fixed context overhead on every request. Add them for the job, remove them after.

🎯 Prompting & delegation

1

Be specific about scope

Name the file and the function. Precise asks prevent broad scanning and keep the diff focused.

2

Plan before large changes

Use plan mode for anything multi-step. A reviewed plan beats an unwound mess.

3

Delegate exploration to subagents

Push wide, independent research into subagents — ideally on a cheaper model — so your main thread stays clean.

4

Drop the anti-laziness language

Skip "be thorough" and all-caps demands. State the goal and the boundaries; let a proactive model work.

Course complete — the meta-principle

Anthropic frames the overarching goal as context engineering: finding the smallest possible set of high-signal tokens that maximize the likelihood of the outcome you want. Every technique in this course — clearing, compacting, scoping, CLAUDE.md, subagents, the right model — is a different way to serve that one principle. In Claude Code, more context doesn't mean better results. Signal density does.
